# 数据可溯源的报告生成（data-grounded reporting）

## 适用场景
生成每日/每周总结、审查报告，或任何含「逐项明细」（逐题、逐文件、逐 commit）的结构化报告；明细依赖外部数据（本地代码、git diff/status、日志、网页资料）。本技能同时管辖这些报告的配套落盘跟踪文档（如「未完成题目.md」）、报告输出结构约定，以及此类技能文档自身的维护纪律。

## 核心纪律

1. **禁止编造逐项明细**：每项细节必须来自可获取的数据源（本地文件、git 历史、用户提供、可检索网页）；拿不到就明说，不靠推理脑补。

2. **先探测、后承诺**：动笔前先验证每个明细部分的数据源是否可得；验证通过才写进计划，失败就主动提出砍掉或替换，不默默跳过。探测时同时确认「最廉价权威源」：能靠 git 状态或记录文档拿到的数据，不做全量文件遍历（见纪律 11）。

3. **主动上报**：数据不可得时用一句话说明并提供替代方案，征得同意后继续，别让用户从思考链里发现。（真实教训：用户因「搜不到具体题目」删掉了每日总结中的「题目大意」小项——本可更早主动提出。）

4. **口径由数据源定义，不由标签定义**：总结覆盖的窗口由实际数据源决定（如「本次刷的代码」= git 中未提交的改动），不是日历时间；标签与窗口不符就按窗口改名（用「本次总结」，不用「今日总结」）。

5. **未完成/遗漏判定标准显式枚举**：如「只 return 固定值」也算未实现；标准写进管辖技能，随技能维护，不靠临场模糊判断。本仓库「未实现题目」判定至少含：①题单中尚未解答的题；②任意被修改过的「说明」文档中标记为「跳过」的章节。

6. **未完成项落盘跟踪**：发现未完成/遗漏项时写入工作区持久文档（如「未完成题目.md」），并注明题号 + 分类/子目录等定位信息，供后续会话直接处理；只在对话里提一句等于丢失。

   「未完成题目.md」维护约定（本仓库实测要求）：
   - 动笔前先扫描所有「说明」文档：说明文档 = 分类目录下的无扩展名知识笔记文件（如 `src/常用数据结构/堆/说明`），内含各章节的「跳过」标注；「跳过」章节中的题目即未实现题目，必须并入未完成题目.md。
   - 写入时**不写日期**；排序为「先章节、再散落的题目」——章节按章节号升序、散落题目按题号升序。
   - 更新触发点：任何说明文档被修改（尤其新增/变更跳过章节）后，必须重新扫描并把新跳过章节并入未完成题目.md。

7. **重复性总结/提交工作流固化决策默认值**：哪些动作自动执行（如提交并推送）、哪些一律拒绝（如修改代码）、会话/文档的固定命名，全部预先写死在技能里，运行中不再逐次询问用户。本仓库会话标题固定格式：`yyyy-mm-dd 刷题数: x`（x = 本次统计的刷题数）。

8. **报告结构约定**：
   - 结构调整顺序：总量统计放最开头，再逐项分析，再整体审查，最后行动（提交/推送）。
   - **统计类数据静默落盘**：总量统计下的明细分布（如各章节分类计数表）不再输出到报告正文，写入持久记录文档（记录总计已完成题数 + 各章节分布），报告只呈现总量结论。
   - **合并实质重复的章节**：如「代码优化建议」与「每题差距分析」实质重复时，前者并入后者，不并列输出。
   - **无问题的例行章节静默**：例行状态类章节（如提交结果、会话标题）若无异常则不再输出，只在有问题时才出现在报告中。

9. **可行性是动态的**：本轮搜不到的数据下轮可能可得；不写死「某数据源不可用」，每轮重新探测，表述用「本轮不可得，已砍/已换」。

10. **用户中途修改要求**：把修改落到管辖该任务的技能并确认生效，再按新要求重跑；新要求含不可得明细时回到纪律 2/3。**修改文档/技能前先给预览**：用户要求改动文档时，先展示修改后的文档并逐条注明「改了什么、为什么」，经确认后再发起实际修改（写文件/改技能），不要直接动手。**修改任何技能前先加载 skill-creator**（用户会检查是否触发）：触发不依赖用户措辞——任务说「总结」「执行」但只要涉及改动 SKILL.md（含附带修改）就必须先加载；改完再按 skill-creator 约束复核一遍才交付。**精简审查三标准**：①冗余——删后不影响技能效用；②语义重复——前后文已提及；③原因解释形/非指令形语句。典型删除对象：括号自注，如「（git 口径，一次收集两处复用）」——数据来源与复用原则正文已声明，自注同时犯②③两条。只保留必要的指令形内容，技能维护是持续删减，不是越改越长。

11. **数据来源选最廉价权威源**：枚举「本次涉及的文件」（新增/改动）直接查 `git status`（配合 `git diff` 看改动内容），不遍历全量文件树逐个统计；总量/分布类数据已有记录文档的（如总计完成题数、各章节分布）直接引用记录，不再重新扫描全部文件计算。一旦记录文档建立，就禁止回到「扫描所有文件」的旧做法。

12. **步骤合并与数据复用**：工作流中相邻步骤若消费同一数据源，合并为一步，或让后续步骤直接复用前序步骤已取得的数据，不重复枚举。实测：daily-summary 的「统计总计完成题数」与「识别本次刷题（git 未提交部分）」同源（都依赖 git status + 记录文档），用户要求合并为一步——先取 git status 清单识别本次文件，再从记录文档补总量。

13. **数据格式统一引用**：数据在定义章（如 daily-summary 的「统计与识别」章）给出格式后，后续所有步骤引用该数据必须使用**完全相同的格式/术语**，禁止同义改写、另起格式或局部重述；交付前逐章核对引用一致性（例如后续步骤提到的「本次题目数」「各章节分布」必须与定义章格式逐字一致）。用户曾要求：将后续步骤中提到的数据统一修改为「统计与识别」章中的格式，并据此复核整个技能。

## 反模式
- 用推理补全明细，生成「看起来合理」的逐项内容。
- 把「本轮检索失败」写成「该工具不可用」，形成长期自我设限。
- 计划里承诺某明细部分，却不先验证数据源。
- 未完成项/待办只留在对话里，不落盘、无分类。
- 每次总结重复询问「要不要提交/推送/改代码」——默认值应已在技能里定死。
- 未扫描说明文档就直接维护未完成题目.md，遗漏「跳过」章节。
- 报告中重复输出已记录到记录文档的统计明细，或并列输出实质重复的章节。
- 不经预览直接改动用户文档/技能，等用户事后纠正。
- 全量遍历文件树来枚举改动文件——`git status` 一行可得。
- 相邻步骤重复枚举同一数据源（统计完成题数与识别本次刷题各扫一遍文件），应合并步骤或复用前序数据。
- 修改技能时不加载 skill-creator、不做「冗余/重复/解释形」精简审查，把技能越改越长；等用户明确说「改skill」才加载——任务隐式涉及 SKILL.md 改动（如「总结」「执行」流程中的附带修正）也要先加载。
- 后续步骤引用数据时同义改写或另起格式，与定义章（统计与识别）格式不一致。
